# Data subject request

1. Route requests to the privacy owner and a restricted ticket. Verify identity without collecting unnecessary new identity data. Record type, scope, received/deadline dates, identity-verification basis and any authorized agent.
2. Check operational blockers and preservation duties. In the admin **Privacy & retention** page, place a reasoned legal hold on the exact user ID *before* a deletion or expiry run. An active hold blocks account deletion and expiry redaction. Record the case reference and expiry; release with a reason when preservation ends. Do not assume an expired or released hold still protects the subject.
3. For an account access request, use the authenticated JSON export as a starting point. Separately review PostgreSQL, private KYC/delivery-proof/support objects, logs, support, payment processors, analytics, backups and subprocessors. Redact third-party data and secrets before secure delivery; expire the delivery link.
4. For deletion, direct the customer through the purpose-bound OTP account-deletion flow. The transaction removes sessions, OTP challenges and disposable account data immediately, pseudonymizes direct identifiers and records an expiry deadline. It records owned KYC file keys before deleting disposable seller applications; the files are removed asynchronously from the durable queue. Active orders, refunds, disputes, seller/rider/platform duties and legal holds prevent premature deletion. Communicate retained categories and exemptions to the requester.
5. The hourly worker processes up to 100 private-file tasks and 100 eligible erasure requests per run. It skips active holds, retries storage failures and pauses failed scheduled retries for 24 hours. In **Privacy & retention**, watch due counts, pending private files, failed attempts and processing history; an authorized manager may run a manual batch after resolving the cause. A request is `PURGED` only after transaction redaction and queued private-file cleanup both complete.
6. Verify the exact user's database status, private-object removal and audit history. Do not interpret a successful run count as proof that every storage system, log, backup or external processor is clean. New server-owned support attachments are included in the resumable retention manifest and removed with the customer's ticket snapshots. Legacy ticket attachment strings have no trustworthy object-ownership record; their references are cleared but their bytes need a separately approved inventory/remediation procedure. Private KYC/support objects orphaned before ownership tracking, or by uploads that never committed a row, still require an inventory sweep. Review backup/subprocessor expiry under their own policies.
7. Respond by the recorded deadline and retain only the request evidence required by an approved policy. The baseline 1,830-day transaction snapshot period is a technical default, not legal sign-off; Nepal counsel must approve the final period and exemptions before launch.

## Private-evidence reconciliation

- Build the API, use the deployment's read-only PostgreSQL credentials and matching `STORAGE_PROVIDER`/storage configuration, then run `node scripts/inventory-private-evidence.mjs --output /secure/new-private-evidence-report.jsonl` from the repository root. The output path must not already exist; the report is created with mode 0600. For local storage, `STORAGE_LOCAL_DIR` is resolved relative to `apps/api`, as it is at runtime. For S3, the tool uses signed, paginated `ListObjectsV2` reads. It never reads file bytes, changes the database or removes an object.
- Review the summary counts and restricted report with the privacy owner. A report without its final `summary` line is incomplete and must not be used for a deletion decision. `knownOwnerUntracked` and `heldUntracked` have an application or support-ticket row but no file/queue reference; `unknownOwnerUntracked` has no surviving owner row, so its subject and any legal hold cannot be inferred. `recentUntracked` is under 72 hours old and may still be an in-flight upload. `deletedButPresent` signals a queue/storage inconsistency. `invalidKey` requires manual inspection. `legacyTicketReferences` are untrusted client-supplied strings, not proof of object ownership.
- Reconcile each finding against incident logs, backups, case records and legal holds. Do not delete an unknown object or queue it under a guessed user. Obtain a documented preservation/deletion decision and separately approved execution plan for old orphans. Restrict access to the report, record who reviewed it, and securely expire the report after the case closes. A clean report is not proof that backups or subprocessors have expired.
- New support replies accept one validated photo/PDF per message through a private, ticket-scoped upload route. Reads re-check customer ownership or `support.view`; staff writes require `support.respond`. The ticket has a 20-file ceiling. Existing legacy string references remain untrusted historical data, not downloadable through the new route, until redacted by the retention worker or handled under the approved legacy procedure.
